# Firedoor v0.3 — Safety and Evidence Boundaries

## What may run

A future verifier may execute a narrowly fixed HTTP probe from each existing Firedoor-owned workload Pod to the **observed** Pod IP of another owned workload, over TCP/8080. This must be opt-in, bounded, and limited to the verified local `kind-firedoor-local` context. `kubectl exec` causes a process to run inside a Pod, so it must not be misrepresented as a read-only Kubernetes API operation.

## What must not run

- No remote/production cluster contexts and no non-Firedoor namespaces.
- No arbitrary IPs/hostnames provided by the CLI operator.
- No `kubectl apply`, `delete`, `patch`, `run`, or Terraform `apply`/`destroy`.
- No Pod replacement, NetworkPolicy mutation, RBAC changes, or privilege escalation.
- No unbounded retries, long-running traffic generators, port scans, or offensive scenarios.
- No passing verdict without inspected ownership and observed evidence.

## Operator prerequisites

1. Confirm Git branch `feat/v03-live-verification`.
2. Verify current Kubernetes context exactly `kind-firedoor-local` and kind cluster `firedoor-local`.
3. Verify that all three Workloads and Pods are ready and owned by the testbed.
4. Independently check the Terraform `active_profile` output before choosing `baseline` or `hardened`.
5. Treat network failures as observed reachability results, not independent attribution to Calico.

## Slice 1 limitations

The `liveverify` package produces a plan only. No live network traffic is generated by its tests. The later Slice 2 implementation must apply these boundaries at runtime and emit clear error and inconclusive outcomes rather than assuming they are automatically enforced by a valid plan.
